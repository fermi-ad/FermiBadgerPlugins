## After the GUI run

Both GUI findings are fixed and all five checks pass.

**1. Unstable optics → NaN.** New observable `optics_stable`: `1.0` while the
twiss solves, `0.0` when it doesn't. Advertised on every lattice, with no
`-SETPOINT` twin (it's a flag to constrain, not a target). Both DR templates now
carry `optics_stable > 0.5` as a non-critical constraint.

- [environments/…/__init__.py](../plugins/environments/VirtualAccelerator_MADXSuite/__init__.py) — `OPTICS_STABLE`, appended in `_deduce_observables()`, excluded from design setpoints
- [interfaces/…/__init__.py](../plugins/interfaces/VirtualAccelerator_MADXSuiteInterface/__init__.py) — one branch at the top of `_read_observable`

Caveat worth knowing: the *objective* is still NaN at those points, and xopt does
not drop NaN rows before fitting the GP. The constraint steers the acquisition
away from the region; it doesn't clean the training data. Say the word if you
want the `-SETPOINT` channels to return a large finite penalty instead.

**2. `Center point keys must match vocs variable names`.** Root cause is Badger's
cache, not the lattice: `factory.load_plugin` builds `configs['variables']` once
from an env instance using the *default* lattice in `configs.yaml` (the Delivery
Ring) and never refreshes it — `iq2`/`iq3`/`iq74` never reached the variable
table, nothing got selected, and `get_variables([])` returned `{}` against a
three-variable vocs. (`configs['observations']` aliases the class list, so it
*does* track the template's lattice — that's why only variables broke.) Fixed
with Badger's supported escape hatch in
[Xfer400MeV_example.yaml](../tuning_templates/Xfer400MeV_example.yaml):

```yaml
additional_variables: [iq2, iq3, iq74]
```

That path resolves bounds through an env built from the template's own params.
Any future template on a non-default lattice needs the same list — and
[VA_template_integration_test.py](../tests/VA_template_integration_test.py) now
walks every shipped template and fails if a vocs variable is in neither list,
isn't a real knob of that lattice, or names an unadvertised observable. It caught
the objective mismatch while I was writing it.

Also in the smoke test: `i_dqd → 0` drives the ring unstable, asserts
`optics_stable == 0.0` and `qx` NaN, then restores. Docs, log, and the
`badger-gotchas` memory are updated; the MAD-X artifacts are deleted again.

Worth re-running `Xfer400MeV_example.yaml` in `-mini` to confirm the table fills.

## After the second `-mini` run

Neither the template nor the plugin hard-codes anything: Badger's `-mini`
variable table keeps its *own* copy of the env configs, captured in
`select_env()` from the plugin's `configs.yaml` defaults, and rebuilds an
environment from that copy on **every** `refresh_current_values()`
(`badger/gui/mini/components/var_table.py:769`). That's both
symptoms at once — the repeated `Converting sequence "full"` (the Delivery Ring
being re-parsed) and `Cannot read 'iq2'` (a Delivery Ring env being asked for a
400 MeV knob). Badger even flags it: `# TODO: Use a cached env` in `add_var`.

Fixed all three ways, since any one alone leaves a sharp edge:

**1. Badger patch** —
[badger-mini-var-table-env-configs.patch](../patches/badger-mini-var-table-env-configs.patch),
applied to FermiBadger_env and listed in [patches/README.md](../patches/README.md).
Re-runs `add_var()` right after the template's params reach the editor and drops
the stale `var_table.env`, so the table tracks the template's lattice.

**2. Tolerant reads** — `_read_setting` warns and returns NaN for a channel this
lattice doesn't have, rather than raising. One unknown name in a stale table
shouldn't abort a template load. `set_values` still raises: silently dropping a
write is a different matter.

**3. Lattice cache** — `_LATTICE_CACHE`, keyed on (resolved path, sequence),
holding the `Madx` and a pristine design `Line`. Every instance works on
`design_line.copy()`, which carries the whole xdeps graph across:

| | fresh load | cached |
|---|---|---|
| Delivery Ring environment | 9.9 s | **1.3 s** |

One correction to the cache as first written: it stored the loading instance's
own `Line`, so the second environment inherited the first one's detuning. The
smoke test caught it. Now every instance — the loader included — takes
`design_line.copy()`, and the test asserts both the speed (< 3 s) and the
independence (design `qx = 9.6489` after the first was detuned to 9.4749). Only
lattices whose `:=` rewrite verified get cached, so the fallback reload path
(which replaces `self._madx`) can never touch a cached entry.

All five checks pass: the `madx_deferred` self-check, the deferred-expressions
test (tune sweep 220→10.024228 … 260→9.285527, both lattices), the smoke test,
the template integration test (all three MADXSuite templates GUI-loadable), and
the GUI param editor test. Docs, log and the `badger-gotchas` memory are
updated; the MAD-X artifacts are deleted. Nothing committed yet.

## The two remaining DR loads

They were Badger's, not the template's. To fill the browsable variable list,
`factory.load_plugin` instantiates the environment with the **plugin's default
params** and calls `env.get_bounds(m_env.variables)` — the Delivery Ring, 9.3 s,
whatever lattice the template names. Once per *process*, and the optimization
runs in a spawned `multiprocessing.Process`, so the in-memory lattice cache
can't help the second one. Hence exactly twice: template load, then run start.

So the environment stopped loading anything in `__init__`. It writes the deduced
lists to a sidecar beside the lattice and defers the parse:

```
sim_configs/DeliveryRing/mu2e-dr-model-….madx.b3c3b5a7.varcache.json   84 KB
{"stamp": {mtime, size, sequence, rel_range, zero_half_range,
           bpm_name_pattern, twiss_init}, "variables": {…}, "observables": […]}
```

Construction reads that file; `_ensure_lattice()` does the MAD-X parse on the
first call that actually needs the Line (`get_variables`, `set_variables`,
`get_observables`, or bounds for a name not already listed). The hash in the
filename is over the params that shape the lists, so the plugin defaults and a
template with different ranges get their own file instead of invalidating each
other; the stamp catches an edited lattice.

| fresh process, `get_env('VirtualAccelerator_MADXSuite')` | |
|---|---|
| before | 9.3 s, Delivery Ring parsed |
| after | **1.2 s**, nothing parsed (mostly the xtrack import) |

The template's own lattice is parsed once, when the variable table first reads a
value. Sidecars and the MAD-X output files are now gitignored.

**One bug found on the way:** `DR_BetatronTunes_sim.yaml` had
`zero_half_range: -1.9`, so every zero-valued knob got bounds `[1.9, -1.9]`.
Template corrected to `1.9`, and `_bounds_around()` now takes `abs()` so no
template can do it again.

All five checks pass, with the smoke test asserting the lazy construction leaves
`_line` unset, that known-variable bounds don't trigger a parse, that the first
observable read does, and that the stamp records every param that shapes the
lists.

## The table's rows

The flood above had a cause worth removing rather than muffling: under a 400 MeV
template the `-mini` table was still listing 2284 Delivery Ring knobs. Its rows
come from `routine_page.vars_env`, built in `select_env()` from the factory's
`configs["variables"]` — computed once, from an environment carrying the
plugin's `configs.yaml` defaults.

[badger-mini-var-table-env-configs.patch](../patches/badger-mini-var-table-env-configs.patch)
now covers both halves of that staleness. After refreshing the table's env
configs it rebuilds `vars_env` the way `factory.load_plugin` builds the cached
one — `instantiate_env()` on the template's params, then
`get_bounds(type(env).variables)` — inside a try/except that logs and keeps the
cached list if the environment can't be built, so a template on the default
lattice behaves exactly as before.

| `Xfer400MeV_example.yaml`, variable table | rows |
|---|---|
| before | 2284 (Delivery Ring) |
| after | **124** (its own lattice) |

With the sidecar cache warm that rebuild parses no MAD-X. Re-apply the patch
with `-p1` from `site-packages`; the file now carries both hunks, so revert the
old copy first if you have it applied elsewhere.

[VA_template_integration_test.py](../tests/VA_template_integration_test.py) runs
the patch's own construction for every shipped template and asserts a
non-default lattice yields a different list — all five checks pass. Nothing
committed yet.
